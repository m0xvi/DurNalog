# Git и релизы TurNalog — коротко и по шагам

Схема работы: в ветке `main` живут **исходники**, а готовые EXE раздаются
через **GitHub Releases**. Релиз создаётся автоматически, когда вы пушите
**тег** вида `v2.5` — GitHub Actions собирает EXE на своём сервере и
публикует архив `TurNalog-win64.zip`.

---

## 1. Повседневный цикл (после любых правок кода)

```
git add -A
git commit -m "что изменили"
git push
```

Это просто обновляет код в репозитории. **Релиз при этом НЕ создаётся** —
и это нормально: пользователи продолжают качать последнюю опубликованную
версию, пока вы не решите выпустить новую.

## 2. Выпустить релиз

1. (желательно) поднимите версию в `main.py`: `APP_VERSION = "2.5"` и
   закоммитьте её вместе с правками;
2. создайте тег и запушьте его:

```
git tag v2.5
git push origin v2.5
```

3. Всё дальше происходит само: вкладка **Actions** → запуск «Build EXE»
   (~3–5 минут) → во вкладке **Releases** появляется релиз `v2.5` с архивом
   `TurNalog-win64.zip`. Скачивайте и раздавайте бухгалтерии именно его.

> Тег должен указывать на коммит, в котором уже лежит
> `.github/workflows/build-exe.yml`, иначе запуск просто не стартует.

## 3. «Как запушить в релизы ещё раз?»

Теги уникальны, поэтому:

- **Обычный случай** — новые правки → новый тег: `v2.5`, потом `v2.6` и т.д.
- **Мелкая починка той же версии** — тег `v2.5.1` (или `v2.5-hotfix`).
- **Нужно именно пересоздать тот же тег** (например, релиз собрался криво):

```
git tag -d v2.5                 # удалить локально
git push origin :refs/tags/v2.5 # удалить на GitHub
git tag v2.5                    # создать заново на ТЕКУЩЕМ коммите
git push origin v2.5
```

После пуша тега Actions соберут и опубликуют релиз заново (старый релиз с
тем же именем тега будет перезаписан/обновлён).

## 4. Ручной релиз (если Actions недоступны)

```
build.bat          → соберёт dist\TurNalog\TurNalog.exe
make_release.bat   → упакует папку в TurNalog-win64.zip
```

Затем на GitHub: **Releases → Draft new release** → введите tag `v2.5` →
прикрепите `TurNalog-win64.zip` → **Publish release**.

## 5. Если что-то пошло не так

| Симптом | Причина / решение |
|---|---|
| После пуша тега в Actions пусто | Тег стоит на старом коммите без workflow. Пересоздайте тег (п. 3). Проверить: на GitHub откройте тег — там должна быть папка `.github/workflows`. |
| Запуск упал с 403 на «Publish release» | Приватный репозиторий: токену нужны права записи. В `build-exe.yml` должно быть `permissions: contents: write` (уже есть). |
| Во вкладке Actions пусто вообще | Приватный репозиторий: зайдите в Actions один раз и нажмите кнопку включения воркфлоу. |
| Артефакт из Actions не скачивается (PR_CONNECT_RESET) | Сеть режет хранилище артефактов. Качайте **релиз** (вкладка Releases) — он раздаётся с другого CDN; либо смените сеть/браузер. |
| Ошибка в сборке | Actions → запуск → красный шаг → скопируйте последние строки лога и смотрите/шлите разработчику. Чаще всего — проблема с pip/сетью: просто перезапустите запуск (кнопка Re-run). |

## 6. Полезные команды (шпаргалка)

```
git status                     # что изменилось
git log --oneline -10          # последние коммиты
git tag                        # список тегов
git tag -d v2.5                # удалить тег локально
git push origin :refs/tags/v2.5# удалить тег на GitHub
git push --tags                # запушить все теги разом
git pull                       # забрать изменения с GitHub
```

## 7. Соглашение по версиям

- `v2.5` — обычный выпуск; `v2.5.1` — починка; `v3.0` — большие изменения.
- Держите `APP_VERSION` в `main.py` (отображается в сайдбаре) одинаковым с
  тегом — так проще понять, какой EXE у кого установлен.
- Что попадает в EXE: всё, что закоммичено на момент тега. Локальные файлы
  (`turnalog_history.db`, `turnalog_config.json`, логи) в репозиторий и в
  релиз не попадают — они живут на компьютере пользователя.
