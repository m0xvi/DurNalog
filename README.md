# DurNalog (TurNalog) — v3.39

Интерфейс — дизайнерский пакет `TurNalog_ui/` (customtkinter),
боевая логика — `core.py`/`db.py`/`agents.py`/`tax.py`, связка — `main.py`
(хуки `hook_*`: обработка, история, настройки, пользователи, БД, авторизация).

Редизайн по макету дизайнера (`ui_theme.py` — палитра/шрифты):
тёмно-синий сайдбар с цветными точками отелей, белые карточки шагов,
зоны файлов вместо текстовых полей, квартал и чекбокс дублей на форме,
настройки с левым меню и свёрнутыми формулами, стильные таблицы и тосты.
Квартальные налоговые правила сохранены; TravelLine запрашивает только
выбранный период и хранит его локальный снимок в SQLite.

Десктоп-приложение (Windows) для расчёта туристического налога по выгрузкам
из отельных систем. Python + customtkinter, сборка в EXE через PyInstaller.

## Интерфейс

Тема — фиксированно **светлая**. При запуске — **окно входа**: пользователи
хранятся в локальной БД (пароли — в виде хешей). При первом запуске создаётся
`admin / admin` — смените пароль.

**Расположение БД** выбирается при первом запуске («рядом с приложением» или
общая/сетевая папка) и меняется в «⚙ Настройки → Данные» (при желании — с
копированием текущей базы). Общая папка = общие история, дубли и пользователи
для нескольких компьютеров; смена пути применяется без перезапуска.

Роли:
- **администратор** — все отели, История, «⚙ Настройки» (в т.ч. вкладки
  «Агенты» и «Пользователи»: добавить/удалить, сменить пароль; последнего
  админа удалить нельзя);
- **пользователь отеля** — видит только свой отель и историю по нему.

Боковая навигация: **Чайковский · Дона · Усадьба · История · ⚙ Настройки**
(по правам). Каждый отель — «карточки-шаги»: 1) исходные файлы →
2) обработка. Диалоги автоматически подстраивают высоту под содержимое.
Обработка идёт в фоновом потоке, результат — в статус-баре и сводке;
журнал — `turnalog.log`.

### Настройки (⚙)

По каждому отелю отдельно настраиваются:
- ставка налога, %; минимум за ночь, ₽;
- «налог включён в цену» (делитель 100+ставка) или начисление сверху (/100);
- **«считать налог от стоимости с комиссией (100%)»** — включён по
  умолчанию: цена в файле — это нетто (без комиссии агента), база каждой
  строки восстанавливается до 100% (Стоимость/(100−K)×100), налог считается
  от неё. Выключайте, только если в файле уже полные цены гостя;
- для **Чайковского** — переключатель **«Включать допуслуги в налоговую
  базу»** (включён по умолчанию): в базу добавляются все допуслуги;
- для **Доны** — отдельный переключатель **«Включать „Продление номера“ в
  налоговую базу»** (включён по умолчанию): учитывается только сумма услуги с
  таким названием, остальные допуслуги в налоговую базу не входят;
- в обоих отчётах после «Стоимость с комиссией» показываются «Допуслуги» и
  «Стоимость для налога»; для Доны рядом указана отдельная сумма «Продление номера»;
- в разделе **«Агенты → Кампании TL…»** отдельно для Чайковского и Доны
  указываются точные названия кампаний TravelLine (`total.discounts[].name`),
  для которых скидка остаётся вычтенной из налоговой базы. Для остальных
  кампаний скидка по умолчанию добавляется обратно. Пустой список означает,
  что добавляются все скидки;
- порог метода «ставка» — вручную или автоматически (мин×(100+ставка)/ставка);
- **шаблоны Excel-формул** (Сут.ставка / Метод / Налог) с плейсхолдерами
  `{P} {N} {R} {M} {T} {min} {rate} {div}`, кнопками «Показать формулы» и
  «Сбросить по умолчанию».

Там же — общая вкладка **«Агенты»** (список слева, карточка справа):
- ➕ добавлять / ✕ удалять своих агентов;
- **«Применяется к»** — галочки отелей (Чайковский/Дона/Усадьба);
- **синонимы** названий в отчётах (через запятую);
- **плавающая комиссия по периодам**: строки «с … по … %», пустые даты =
  базовая ставка; для брони берётся период, содержащий дату заезда;
- чекбокс **«Автоматически устанавливать комиссию 0%»** — обратимый
  индивидуальный override распознанного агента. Настроенные проценты и периоды
  не переписываются и снова применяются после снятия галочки;
- кнопка **«Кампании TL…»** открывает исключения скидок TravelLine внутри
  раздела «Агенты»; отдельного пункта навигации нет;
- **Импорт/Экспорт** таблицы агентов (Excel/CSV: Название | Отели |
  Синонимы | С даты | По дату | Комиссия % | Комиссия 0%) — для бэкапа и
  переноса на другой компьютер; несколько строк с одним названием = периоды;
- «Проверить» — тест распознавания источника, с учётом override комиссии 0%.

Распознавание устойчиво к вариантам написания: точное совпадение →
подстрока → транслитерация («Островок» = «Ostrovok») → похожесть ≥ 0.85
для сокращений и опечаток. Нераспознанные источники при запуске Доны
попадают в диалог: сопоставить с агентом / создать нового / 0%.
Всё хранится в `turnalog_config.json` и применяется к новым обработкам.

Там же — вкладка **«Обновления»** (только чтение настроек не требует):
- текущая версия и кнопка **«Проверить сейчас»** — запрос к GitHub Releases;
- **«Скачать и установить»** с прогрессом — ставится поверх EXE-версии,
  данные (настройки, история, БД) сохраняются, приложение перезапускается;
- список изменений найденной версии и кнопка «Страница релиза»;
- галочки **«Проверять при запуске»** (тихо, с уведомлением при находке)
  и «Скачивать автоматически». Ручная установка доступна только в собранной
  EXE-версии; при запуске из исходников кнопки установки отключены.

### Сопоставление колонок

После выбора файла приложение читает его заголовки. Если сохранённого
сопоставления нет (или колонки не совпадают), открывается диалог
«Сопоставление колонок»: для каждого поля приложения (Гость, Стоимость,
Заезд…) выбирается колонка файла — с кнопкой **Автоподбор** по синонимам
(«Сумма»/«Цена»/«Стоимость», «Прибытие»/«Заезд» и т.д.). Обязательные поля
помечены «*». Галочками внизу отмечается, какие **дополнительные колонки
файла перенести в результат**; все неотмеченные игнорируются. Сопоставление
запоминается в `turnalog_config.json` и переиспользуется для следующих файлов;
кнопка «⚙ Настроить колонки…» открывает диалог вручную.

## Отели

- **Чайковский** — «Данные» + «Номера» → листы `1&2`, `нет корпуса`, `1`, `2`
  с формулами налога и подсветкой пропусков.
Все три отеля считают комиссию агентов одинаково: по колонке «Источник»
(Усадьба — по «Организация-заказчик») распознаётся агент из встроенной
таблицы своего отеля (Дона — 57 агентов + прямые каналы; Чайковский и
Усадьба — свои таблицы из файлов отеля, включая плавающие проценты по датам,
например Яндекс 15%→18% с 01.02.2026 или OTELLO 15→17→20%). В результат
добавляются «Комиссия %», «Агент» и «Стоимость без комиссии»
(=Стоимость/(100−K)*100 — восстановление 100% цены из нетто); налог и формулы
обычно считаются от неё. Для строк TravelLine отдельное поле
«Налоговая база TravelLine» задаёт основу проживания для «Стоимость для налога»;
допуслуги добавляются отдельно по настройке отеля. Агентская комиссия не
применяется к восстановленной базе повторно; её ставка и отображение не меняются.
Цена в файле при этом
подписывается «без комиссии». Если встречаются неизвестные
источники, при запуске открывается диалог: сопоставить с существующим
агентом, **создать нового агента глобально** (имя берётся из источника, вписать только %) или оставить
0%; выбор сохраняется и больше не спрашивается.
- **Усадьба** — отчёт UCS Shelter «Доход по номеру» (структура фиксированная,
  сопоставление не нужно).

Битые Excel-выгрузки (невалидный XML в стилях — PMS любят такое) чинятся
автоматически в 5 уровней: короткий rgb → чистка styles.xml → чистка всех
xml → пересборка стилей с сохранением форматов дат → минимальные стили.
Первые три без потерь и молча; последние два показывают предупреждение
в финальном диалоге («…открыт после восстановления…» / «СИЛЬНО повреждён…»).
Совсем нечитаемый файл даёт понятную ошибку с советом пересохранить его
в Excel (Файл → Сохранить как → .xlsx).

## Импорт из TravelLine (Чайковский и Дона)

Вместо ручной выгрузки из вебки — кнопка **«↓ TravelLine»** на экране
обработки (Чайковский/Дона). Нужны `client_id`/`client_secret`/`propertyId`
из кабинета TravelLine (Настройки гостиницы → Подключения API) — вводятся
один раз и хранятся в `turnalog_config.json` на этом компьютере. Для поиска
по датам нужен доступ к PMS API/PropertyReservation, а для подробностей каждой
найденной брони — Read Reservation API. Для Чайковского дополнительно полезен
доступ к номерному фонду через PMS API/PropertyRoom.

Перед выгрузкой выберите один из пресетов: **месяц**, **неделя** или **весь квартал**.
Месяц и неделя ограничены выбранным кварталом отчёта; неделя считается с
понедельника по воскресенье, а на границе квартала обрезается его датами.
Произвольный диапазон дат не задаётся. Период включителен по ночам проживания;
дата фактического выезда ночью не считается.

После выбора пресета TravelLine ищет **только брони, затрагивающие выбранный
период**: через PMS API/PropertyReservation запрашиваются номера броней отдельно
для статусов Active и Cancelled, а подробности загружаются через Read Reservation.
Полная история объекта не запрашивается. API поиска ограничен периодом до 365 дней;
месяц, неделя и квартал укладываются в этот предел. На прогрессе показывается число
найденных броней и сколько из них загружено; детали каждой брони требуют отдельного
API-вызова, поэтому фактическое время зависит от числа броней в выбранном периоде.
TravelLine ограничивает запросы; приложение держит запас к лимиту до 4 000 вызовов
деталей в час и обрабатывает HTTP 429 с `Retry-After`/повторной паузой, которую можно
отменить.

Полные ответы сохраняются сжатыми в локальную БД отдельными снимками периода.
Детали фиксируются партиями по 25 броней; при отмене или закрытии окна загрузки
текущая партия также сохраняется. Повторный запуск за те же даты пропустит уже
сохранённые детали и запросит только недостающие (прогресс возобновляется в течение
24 часов). Завершённый период
можно использовать локально без API или обновить; если обновить не удалось, прежний
снимок остаётся нетронутым. Диалог показывает число броней в выбранном периоде,
число сохранённых периодов, размер сжатых данных и фактический размер файла БД;
файл хранится по пути из «Настройки → Данные» и должен быть защищён как локальные
данные отеля. В деталях брони есть персональные данные TravelLine.

Для поиска по периоду требуется разрешение [PMS API/PropertyReservation](https://www.travelline.ru/dev-portal/docs/api/).
Если его нет, приложение покажет ошибку доступа — оно **не переключится на полную историю**.
Для Чайковского номерной фонд комнат и корпусов сохраняется отдельно; отсутствие
права PMS API/PropertyRoom не блокирует импорт броней, но не позволит заполнить комнаты.

Каждый `roomStays[]` выгружается отдельной строкой: групповая бронь на три
номера даёт три цены и три налоговые базы. Если проживание целиком входит в
выбранный период, сохраняется его сумма. Если период захватывает только часть
проживания, используются только точные ночные суммы из полного `dailyRates`,
которые сходятся с итогом проживания. Без полного или сходящегося списка
`dailyRates` такая частичная строка пропускается и попадает на лист
«Предупреждения периода» — равномерной оценки по ночам нет. Допуслуги для
частичного проживания учитываются только при наличии даты услуги в API;
услуги без даты не добавляются и также отмечаются предупреждением.

Импорт забирает брони с ночами в выбранном периоде (отмены пропускаются),
делит проживание и допуслуги (каждая бронь самопроверяется: итог = проживание +
допы, иначе — предупреждение со списком номеров в логе) и подставляет два
файла: данные (канонический маппинг — диалог колонок не нужен; сумма и
наименования допуслуг, тариф, сумма проживания за период и статус распределения
выводятся отдельными колонками) и заполненный файл «Номера» с № брони и
датами заезда/выезда для точного сопоставления каждого проживания. Полные исходные
`COL_PRICE` и `COL_TOTAL` не меняются, в том числе для групповой брони;
налоговая база и сумма за выбранные ночи у каждой комнаты хранятся отдельно.
Для Чайковского `roomStays[].roomId` из деталей
брони сопоставляется с `id`/`roomId` комнаты в PMS API
[`obtain-accommodation-inventory`](https://www.travelline.ru/dev-portal/docs/api/);
если там нет комнат, приложение дополнительно загружает постраничный список
PropertyRoom `/rooms`. Проверяются оба API-поля `roomId` и `room`; если ID не
совпал, допустимо только уникальное точное совпадение подписи комнаты. Номер
берётся из `displayName` с резервными полями `roomNumber`, `number` или
`name`, корпус — из родительского здания, когда API его передал. Отчёт использует
фактический корпус из API, а не порог номера. Неназначенный номер или неизвестный `roomId` остаётся
пустым — ID API не подставляется как номер комнаты. Кнопка «Просмотр данных
API» открывает книгу с подготовленными листами «Данные»/«Номера» и сырыми
полями броней выбранного периода из локального снимка на листах «Проживания API»/
«Номерной фонд API», чтобы проверить ID и подписи комнат. Для обновления данных
используйте «Обновить только этот период»; отсутствие права PMS API/PropertyRoom
показывается отдельно и не блокирует получение броней за период.
Пустые поля из API можно дополнить отдельным файлом «Номера» — например,
отчётом TravelLine «Заезды» (`ArrivalsReport`), где есть № брони и № комнаты.
При совпадении № брони используется он; если по одной брони в отчёте несколько комнат,
дополнительно можно сопоставить «Заезд» и «Выезд»: номер подставится только
при точном совпадении обеих дат проживания. Если номера брони нет, используется
только однозначное совпадение по ФИО. Неоднозначные случаи остаются пустыми.
Если в ручном отчёте нет корпуса, для числовых номеров корпус записывается
явным значением по правилу: номер <50 — корпус 1, иначе — корпус 2.
В выгрузке также фиксируются названия допуслуг, их общая сумма и отдельная сумма услуги
«Продление номера» для правила налоговой базы Доны. Известные коды TravelLine
автоматически сопоставляются с агентами
Чайковского и используют существующие ставки из таблицы агента; соответствия
сохраняются и не требуют ручного выбора. Для TravelLine Booking Engine (сайт)
задана ставка 4% (проверьте свой договор; можно изменить в «Настройки → Агенты»),
для брони со стойки — 0%. `CMB` (агрегатор Comfort Booking) оставлен для ручной
проверки: его комиссия состоит из 2% агрегатора плюс комиссия подканала, а один
код не определяет итоговую ставку. TravelLine возвращает `dailyRates` и
суммы проживания уже со скидкой; приложение не вычитает скидку повторно.
Для налоговой базы по умолчанию к цене проживания добавляется агрегированная
скидка: например, 88 448,20 ₽ + 551,80 ₽ = 89 000 ₽. В разделе
«Настройки → Агенты → Кампании TL…» можно внести точные
`total.discounts[].name`, для которых скидка должна остаться вычтенной.
Исходная стоимость проживания (`COL_PRICE`) и `COL_TOTAL` (итог
брони из API) не меняются. В отдельных полях показываются «Стоимость проживания за выбранный период
TravelLine» и «Налоговая база TravelLine»; последняя используется как основа
«Стоимость для налога», к которой затем по настройке отеля добавляются
допустимые допуслуги. Процент комиссии агента не применяется
к этой основе повторно, ставки агентов не меняются. Названия скидок/кампаний
видны в аудите API, имена гостей в диагностическом JSON маскируются.
В частичном периоде агрегированная скидка добавляется к базе только если
`dailyRates` позволяют однозначно определить затронутую ночь/ночи; иначе
используется фактический тариф выбранных ночей со скидкой и выводится
предупреждение — сумма скидки не распределяется наугад. Для проживания,
целиком попавшего в диапазон, остаётся действующее правило: скидка добавляется
к базе по умолчанию, кроме выбранных кампаний-исключений. `priceAfterTax`
означает «после налогов», не «после комиссии»; API комиссию отдельным полем
не отдаёт. Диагностический зонд —
`tools/tl_probe.py`.
Загрузка идёт в модальном окне с прогресс-баром и кнопкой «Отмена».
Тайм-аут ответа и другие временные сетевые ошибки (тайм-аут — 90 секунд)
автоматически повторяются один раз; если попытки не помогут, ошибка укажет этап
(номерной фонд, получение списка или конкретная бронь). При HTTP 401 приложение
один раз перевыпускает токен; если отказ повторится, сообщит, на каком запросе
(номерной фонд, список или конкретная бронь) он произошёл.
401 означает, что API не принял токен; 403 — что у подключения нет доступа.
Для реальной проверки API, если зонд нашёл локальный `*_full.json`, ответьте
`n` на вопрос об offline-режиме; ответ `y` проверяет только сохранённый файл.
Проверено зондом на 8186 за Q3 2026: допы входят в roomStays.total
(гипотеза B, 81/81 броней, расхождений 0) — импорт вычитает их автоматически.

## История и переход кварталов (вкладка «История»)

При обработке выбирается квартал отчёта; в `turnalog_history.db` (SQLite,
рядом с EXE) сохраняются копии исходного и итогового файлов и распознанные
брони. Гость, попавший в два квартальных отчёта (то же ФИО + пересечение дат
или тот же № брони), во втором отчёте помечается **фиолетовым** с примечанием,
куда он уже попал; налог не пересчитывается (пометка для бухгалтера).
В истории — список отчётов, открытие оригинала/результата, удаление,
просмотр дублей.

## Расчёт налога (общий, `tax.py`)

```
Сут.ставка = Стоимость / Ночей
Метод      = ЕСЛИ(Сут.ставка >= 5100; "ставка"; "мин.ставка")
Налог      = ОКРУГЛ(ЕСЛИ(Метод="мин.ставка"; Ночей*100; Стоимость/102*2); 2)
```

Значения по умолчанию: ставка 2% (2026 г., включена в цену), минимум
100 ₽/сутки, порог 5100. Все параметры и формулы меняются в окне
«⚙ Настройки» по каждому отелю; дефолты — `DEFAULT_TAX` в `tax.py`.

## Подсветки в итоговых файлах

красный — нет № комнаты (Чайковский) · жёлтый — нет гостя / неизвестный
агент · оранжевый — нет дат · голубой — нет стоимости · фиолетовый —
переход кварталов · зелёный — итоги.

## Структура кода

- `main.py` — GUI (редизайн v2.1), обработка, диалог сопоставления колонок
- `schemas.py` — поля входных файлов + синонимы для автоподбора
- `agents.py` — таблица агентов Доны и нечёткое сопоставление источников
- `tax.py` — константы/формулы налога, разбор цен и дат
- `db.py` — SQLite-история отчётов и поиск дублей
- `tests/` — pytest (`python -m pytest tests -q`)

## Запуск и сборка

```
build.bat        # Windows: venv + зависимости + PyInstaller → dist\TurNalog\TurNalog.exe
```

Или без сборки: `pip install -r requirements.txt && python main.py`.

## Релизы (EXE в GitHub Releases, исходники в main)

В репозитории только исходники (`build/`, `dist/`, БД и логи — в .gitignore).
EXE раздаётся через Releases двумя способами:

**Авто:** на каждый тег `v*` GitHub Actions (`.github/workflows/build-exe.yml`)
сам собирает EXE на windows-latest и публикует релиз с архивом
`TurNalog-win64.zip`:

```
git tag v2.3
git push origin v2.3
```

**Вручную:** `build.bat`, затем `make_release.bat` — упакует dist в
`TurNalog-win64.zip`; на GitHub: Releases → Draft new release → tag `v2.3` →
прикрепить zip → Publish.
